# Dokiments UI

As an elite Fullstack Engineer and Award-Winning UI/UX Designer specialized in high-conversion marketing sites and ultra-clean dashboard apps:

## 1. Code Architecture & Component Hygiene

- **Strict Anti-Bloat Rule:** NEVER write multiple sub-components within the same file. If a UI area contains a distinct, reusable subpart, it _must_ be extracted into its own file inside its respective directory. Keep component files short, focused, and single-purpose to maintain an accessible codebase for junior/mid-level developers.
- **Component Style:** All components must be written as TypeScript arrow functions with explicit prop interfaces (`interface Props {}`). They should also include their component name as their first classname (e.g., `<div className="template-card">` for `TemplateCard`).
- **Storybook Coverage:** Every new component must include a colocated story file within its folder (`stories/[component-name].stories.tsx`).
- **Storybook Sidebar Titles:** Every story meta must set an explicit `title` grouped by component bucket only (`Commons/Button`, `Dashboard/Sidebar`, `Website/Hero`). Do not allow Storybook to infer paths that expose `stories` as a sidebar nesting level.
- **Component Shape in Practice:** Existing components use either `const Name = ({ … }: NameProps) =>` with a named export or `const Name: FunctionComponent<Props> = …` with a default export. Match the convention of the neighbouring files you are editing; do not convert existing components between the two styles.
- **State Management:** Shared global UI state belongs in `src/stores/ui-store.ts` (today: sidebar collapse, onboarding open state, refresh cooldown). Use it sparingly; prefer props or local React state for localized hierarchies. Server data (templates, saved templates, documents, clients, shares, notifications) lives in TanStack Query hooks under `src/hooks/queries/` with keys from `src/lib/query/keys.ts`, never in Zustand.

## 2. Strict Directory Structure

All UI components must reside exactly within one of these four subdirectories under `src/components/`:

- `src/components/commons/` — Globally reusable foundational atomic elements (buttons, inputs, dropdowns, modals, loaders) that extend DaisyUI with a flat design language.
- `src/components/website/` — High-converting marketing components matching an Awwwards-winning visual standard (editorial typography, sophisticated layouts, immersive dark sections).
- `src/components/dashboard/` — Modular components specifically built for the core user application (data cards, metric tracking, bento modules).
- `src/components/admin/` — Management views, configuration tables, and analytics modules reserved exclusively for privileged accounts. This folder does not exist yet; create it with the first admin-only component.

## 3. Visual & Aesthetic Guidelines (Awwwards x Bento Style)

- **Aesthetic Direction:** Merge a premium, minimalist canvas with "flat design" principles. There is a single light daisyUI theme (`globals.css`); the signed-in app pairs dark `nox-noir` chrome (`--color-app-chrome`) with white content panels, and there is no dark mode or theme toggle. Avoid heavy gradients, soft outer blurs, or realistic skeuomorphism. Use sharp borders, high-contrast typography hierarchies, and intentional whitespace.
- **Bento Grid Dashboard:** Construct dashboard layouts using structured CSS Grid tracks (`grid-cols-1 md:grid-cols-3 lg:grid-cols-4 gap-4`). Every card inside the Bento layout must be a dedicated module from `components/dashboard/`, utilizing flat borders, unified internal padding (`p-6`), and clear structural boundaries.
- **DaisyUI Extension Strategy:** Utilize semantic DaisyUI utility classes, but enforce a flat design aesthetic by overriding radiuses and soft shadows with sharp utility classes (`rounded-md`, `border`, `border-base-content/10`, `shadow-none`).
- **Tokens Over Magic Numbers:** Use Tailwind tokens and DaisyUI classes configured in `src/app/globals.css`. Never use hardcoded hexadecimal colors or arbitrary spacing utilities (e.g., use `p-6` or `gap-4` instead of `p-[23px]`).
- **Typography (two families only):** `Urbanist` is the sole typeface for all body copy and headings — always go through the `font-body`/`font-title` tokens (both resolve to Urbanist) and never reintroduce another family. `Raleway` at weight 900 ("Black") is reserved exclusively for the Dokiments logo — apply `font-logo` + `font-black` to the wordmark and the "D" mark, nowhere else. A third, signature-only family, `Dancing Script` (`font-signature`, `--font-dancing-script`), is reserved for typed e-signatures (`SignatureField`, `SignedSignature`) and must not be used for anything else. Fonts are loaded via `next/font/google` in `src/app/layout.tsx` (`--font-urbanist`, `--font-raleway`, `--font-dancing-script`).
- **Control Hierarchy:** Keep buttons, inputs, and tabs visually distinct. Primary buttons are solid black (`btn-primary`, white text — never golden); `secondary` is a soft grey fill; `outline` is bordered; `ghost` is text-only. All text CTAs across the website and dashboard use the compact rectangular `rounded-field` radius, matching the subscription plan actions; do not use `rounded-box` or `rounded-full` for CTA buttons. Icon-only controls retain their intentional circle/square shapes. Inputs/selects use a slight grey fill (`bg-base-200`) with a calm focus treatment (`focus:border-nox-noir focus:ring-2 focus:ring-nox-noir/15`), never heavy double outlines. Tabs use an underline (bottom-border) indicator so they never read as buttons. Do not use the retired deep-purple utility class; the product palette should rely on `bg-nox-noir`, `bg-golden-harvest`, and the pastel page colors.
- **Dropdowns:** Use the shared `Dropdown` component from `components/commons/dropdown` for every application selection menu. Its exported `dropdownControlClassName` is the canonical sort/filter treatment: a `rounded-field`, `border-steel-mist` control on `bg-base-200`, with compact typography and a calm expanded state. Compose responsive width or size adjustments onto that class instead of creating native `<select>` controls or bespoke menu treatments. Action menus and filters also pass `sheetTitle` so they open as a bottom sheet on phones (see Modals and bottom sheets); field pickers inside forms don't. Dropdown option lists use the same bordered base surface, grouped labels, and checked selected state.
- **Website Hero Discipline:** Marketing hero sections must be high-conversion and edited, built from the dashboard's own visual parts so the site and app feel like one product. Keep one clear promise and two CTAs maximum, and keep all hero content inside the main white hero container (`grid lg:grid-cols-[0.88fr_1.12fr]`, both columns inset `p-3 lg:p-4`).
  - **Left column (`HeroIntro`, client component):** a `rounded-box` intro card that mirrors the dashboard welcome card and walks through the app's process in three plain steps (`hero-intro-steps.ts`). Each step owns a tone, a headline (`lead` + white-highlighted `highlight`) and a description: 01 **Pick a template** (`bg-golden-harvest` — the brand golden, matching the dashboard welcome card — keeps "Business documents without the **blank page.**" as the server-rendered default `h1`), 02 **Add your client** (`bg-play-blue`, My Clients; "Your client's details, **filled in for you.**"), 03 **Send the PDF** (`bg-play-purple`, My Documents; "A polished PDF, **ready to send.**"). The active step sets the card background (`transition-colors duration-500`) and swaps the copy (re-keyed with `feature-tab-details-enter`); the copy block has `lg:min-h-60` so the CTAs never jump between steps. Card order: the white/65 uppercase `Sparkle` pill ("Document workspace"), the step headline (`text-4xl sm:text-5xl`, highlight is a `bg-white` `whitespace-nowrap` mark) and description, `HeroActions` (black primary; Sign In gets a white fill via `secondaryClassName`), then the three `HeroFeatureTile` step buttons in an `ol` (`grid sm:grid-cols-3`), then `HeroCredit`. ## 4. App Shell & Layout Rules

- **Shell Division:** Main app shell pieces live under `src/components/dashboard/`: `app-shell` (composes `AuthGuard`, `Toaster`, `OnboardingLauncher`, banners), `sidebar` (+ `sidebar-item`, `sidebar-onboarding`, `sidebar-feedback`, `sidebar-account`, `sidebar-toggle-button`), `content-container`, `mobile-page-header`, `responsive-header-controls` (`NotificationBell`, `RefreshButton`) and `page-banner`. There is no separate topbar component; the header row is rendered by `AppShell`. Do not prefix these component names with `dashboard`.
- **Header Row:** The header sits on the dark app background above the white main content panel and aligns with the sidebar logo row. It shows _only_ the page title and right-side action items. Personalized copy like `Hello, Anthony!` belongs inside the main canvas panel, never the header. Every page, the Dashboard included, uses the same top bar (`PageBanner` / `MobilePageHeader`) holding the phone menu button (phones only), refresh and notifications; never move those controls into page content. Every top-bar icon control (phone menu, back, refresh, notifications, settings) uses the notification bell's `toneClasses` (`dark` on the noir bar, `light` on pastel bars): borderless, `size-9`, same hover. Never give one control its own border or hover. The Dashboard's top bar is `noir` (the app's black, `pageThemes.Dashboard`) so the golden welcome card stands out below it; the welcome card holds only its pill, greeting and copy.
- **Sub-pages go back from the top bar, never from the content:** Never put a "Back to …" button (or arrow link) in the page content. A sub-page shows a back arrow right before its title in the top bar instead: `PageBackButton` inside `PageBanner` (desktop) and `MobilePageHeader` (phones). On a sub-page the back arrow is the only control before the title: no menu button and no sidebar toggle on any screen size. Routes that are always sub-pages pass `AppShell` a static `back={{ href, label }}` (company page → "Companies", shared document → "Shared with me"). Content that becomes a sub-page at runtime, or knows a better title, calls `usePageHeader({ back, title })` (`src/hooks/use-page-header.ts`, stored as `pageHeader` in `ui-store`, cleared on unmount): the document editor and template picker use it with `back: { label: "My Documents", onClick: leaveSubPage }` and titles "Edit document" / "New document" (picker and new editor) / "Duplicate document"; because these runtime sub-pages have no URL of their own, `DocumentsView` pushes one history entry on the way in (`subPageHistoryKey`), so the browser back button and the phone back gesture return to the list, and `leaveSubPage` goes back through that entry instead of stacking a second list entry. Any new in-place sub-page must do the same; the company page sets the company's name as the title; the shared document sheet sets its back target per viewer. The arrow is named "Back to {label}". Sub-page content starts with `pt-6`, like list pages.
- **User Navigation:** The account lives in `SidebarAccount` at the bottom of the sidebar; never render the raw user email in a header trigger. It is one quiet row under a `border-white/10` divider: avatar, name (bold) over email (truncated), and a ghost log-out `ButtonIcon` (`SignOutIcon`, `aria-label`/`title` "Log out", `text-app-nav`, red only on hover) at its end, never a red full-width button. `InstallAppButton` sits above it styled as a plain sidebar row (it renders nothing when the app can't be installed). Collapsed on desktop: the avatar (named by `title`) above the log-out icon.
- **Sidebar logo (no layout shift):** the wordmark SVG is 16880×2544 (≈6.6:1). Its `next/image` must declare that ratio (`width={120} height={18}`, `h-[18px] w-[120px]`) and `priority`; a square `width/height` reserved a 120px-tall gap on reload until the SVG loaded and pushed the nav down. Apply the same rule to every `next/image`: real intrinsic ratio, explicit size classes.
- **Sidebar UX:** The desktop collapse control lives **in the sidebar, beside the logo** (`SidebarToggleButton`, a `SidebarSimpleIcon` ghost button in the nav-item colours, `lg` only), never in the top bar; desktop has no hamburger at all (the `ListIcon` menu button is for phones, where it opens the drawer). When collapsed, the logo mark is the expand button and swaps to the same sidebar icon on hover; do not add a second toggle in the collapsed view. On phones the drawer shows a close X instead. Keep the logo and nav icons perfectly centered on the vertical centerline. Bottom controls stack in this order: `SidebarOnboarding` ("Getting started"), `SidebarFeedback` ("Send feedback"), the Settings `SidebarItem` (`settingsNavigationItem` from `src/lib/dashboard-navigation.ts`), then `SidebarAccount`.
- **Onboarding tour:** New accounts land with `?welcome=1`, added by `SignUpForm` to both its email redirect and its "Sign up with Google" `next` path (the auth routes and Firebase helpers stay untouched). `OnboardingLauncher`, mounted once in `AppShell`, opens `OnboardingDialog` from that flag and strips it from the URL; open state lives in `ui-store` so the sidebar's "Getting started" row (`SidebarOnboarding`, directly above "Send feedback") reopens the same tour. Steps live in `onboarding-steps.ts`: Welcome ("Hi {first name}!" greeting; its golden image container shows the laptop-on-rock `home-mockup.svg` sitting on the container's bottom edge), then the template system in order — Marketplace → My Templates → My Documents — then My Clients and Plans, each on its area's page tone. Copy is short and plain and names real buttons and pages; each point is a bold label over one lighter sentence, under a large title and a darker lead line. The dialog mirrors the sign-in page: inset by `p-3`, a rounded tone container on the left whose visuals crossfade like `AuthShowcaseSlide` (`hero`, `framed` and `wide` layouts), with the copy, progress and actions on the right. On desktop a small black wordmark sits centred at the top of the image container on every step, outside the crossfading visuals so it never fades. It is full screen below `md`, with a top row holding the wordmark (left) and the close button (right) above the image container, and a centred card from `md` up.
- **Responsive Viewports:** On mobile/tablet, the main content panel scales to full viewport dimensions. The topbar remains pinned/sticky, introducing a navigation trigger beside the title that toggles the sidebar as an off-canvas overlay.

## 4b. Auth Pages

- **Shared shell:** Sign in, sign up, and forgot password all render through `AuthLayout` (`src/components/commons/auth-layout/`). It is a full-viewport white split screen with no website `Header`/`Footer`: the left half (desktop `lg+` only) holds the `AuthShowcase` inside `p-3`, sticky at `h-dvh`; the right half centres a `max-w-md` column with the black "D" mark (`/images/svg/icon-black.svg`, linking home), a centred `font-title` heading, a short description, the form, an optional centred text footer, and `HeroLegal` pinned to the bottom. Auth pages set `viewport.themeColor` to `#ffffff`.
- **Forms stay separate:** Redesigns of the shell must not touch `SignInForm` / `SignUpForm` / `ForgotPasswordForm` internals. Page-level copy (title, description, footer links) lives in the page file.
- **AuthShowcase:** A five-step product tour (Marketplace → Templates → Documents → Workspace → Plans) defined in `auth-showcase-slides.ts`. Each slide is a flat, gradient-free field in its product area's page-banner tone (teal, pink, purple, golden, blue) with the matching illustration framed as a `rounded-box` card and noir editorial copy at the bottom. Slides crossfade; they are all mounted so images are ready before they appear.
- **Stepper timing:** The bottom stepper is an accessible `tablist` (arrow keys move between steps). The active step's progress bar is the autoplay timer: its `auth-showcase-progress` CSS animation in `globals.css` runs 5s and its `animationend` advances the slide, so change the duration there, not in JS. Autoplay pauses on hover/focus and is disabled under `prefers-reduced-motion` (the active bar shows full).
- **Mobile:** The showcase is hidden below `lg`; the form column is the whole page. In its place, the intro (logo, heading, description) becomes a golden `bg-golden-harvest` `rounded-box` panel inset by the same `p-3` gutter as the desktop showcase, with the form below it; from `lg` up the intro is a plain centred header.
- **Sign-in form order:** `GoogleSignInButton` leads (full width, outlined, `rounded-field`), then an "or continue with email" divider, email, password with a right-aligned "Forgot password?" link beneath it, and the black `primary` "Sign in" button directly after the credentials.
- **Promo code:** Optional fields never sit between credentials and their submit button. On **both** `SignInForm` and `SignUpForm` (never an always-open field or callout), the promo field lives inside `PromoCodeDisclosure` (a native `<details>` toggle reading "Have a promo code?") below the submit button. When open it shows the golden callout box (`rounded-box border-golden-harvest/40 bg-golden-harvest/10 p-4`, gift icon, campaign label and code from `activePromoCode`) with the input inside it. It stays mounted while collapsed so the form keeps owning its state and the code still reaches both the submit body and the Google link; when collapsed with a value, the toggle shows the entered code.

## 5. Integrations & Guards

- **Icons:** Use Phosphor Icons (`@phosphor-icons/react`) exclusively for all dashboard controls, navigation, and state indicators.
- **Forms & Validation:** Auth and settings UI must use React Hook Form combined with the modular inputs from `src/components/commons/`. Keep form containers isolated in their own folder tracks.
- **Firebase Infrastructure:** There is no Firebase client SDK in the browser. Firebase Auth and Firestore are called server-side over REST from `src/lib/firebase/server-*.ts` (server-only), configured by `FIREBASE_API_KEY`, `FIREBASE_PROJECT_ID` and `FIREBASE_AUTH_DOMAIN` (no `NEXT_PUBLIC_` prefix). UI talks to `/api/*` routes through the TanStack Query hooks in `src/hooks/queries/`.
- **Dev Auth Bypass:** Local development may bypass auth with the server-only `DEV_AUTH_BYPASS="true"`. It is gated by `NODE_ENV === "development"` in `src/lib/session.ts` and `src/proxy.ts`; keep mock-user logic there rather than scattering it across components.
- **RBAC:** Application roles map to `superadmin`, `free`, `silver`, `gold`, and `special`. Defaults to `free`. Client-side route blocking is enforced by wrapping views with `AuthGuard`, composed within the `AppShell`.

## 6. Marketplace, Templates & Documents

- **Form section icons:** Pair each `TemplateForm` legend with a neutral Phosphor icon: file for document details, user for sender, identification card for recipient, list for content/items, currency for amounts, and signature for closing. Use `size-5`, `shrink-0`, `gap-2`, and `aria-hidden`; retain visible titles without adding explanatory text or decorative icon backgrounds.

- **Document editor forms:** `TemplateForm` uses title-only sections with no explanatory paragraphs: Document details, Your details, Client details (invoice/quotation/receipt; otherwise Recipient details), Items or Content, Amounts, and Signatures & closing. Preserve NDA party labels and hide empty groups. Sections are an accordion of `FormAccordionSection`s (semantic fieldsets whose legend is the toggle button): only one is open at a time, starting with Document details; each ends with a black `primary` "Next" button ("Save" on the last) that marks it complete, closes it and opens the next. Values still flow to the draft on every change, so the button never calls the API. Only Document details starts open, so stories/tests that touch other sections (e.g. the sender block or `ClientPicker` in Client details) must first click that section's header button (accessible name starts with the section title). Use subtle top dividers and `gap-4` between fields. Keep document name in Document details and `ClientPicker` inside Recipient. Party inputs follow name → phone → email → address → BRN. Grouping is presentation-only and must preserve all field keys, values and change callbacks, including unknown saved-template fields in Content.

- **Document layout:** `TemplateDocument` reuses the borderless two-column `TemplateParties`: name → phone number → email → multiline address; BRN follows when present. Optional blank contacts are omitted. Use `mb-8` before metadata/body. `withPartyContacts` adds optional sender/recipient contact inputs for existing templates without rewriting snapshots; prefill uses the same fields. Preserve NDA Disclosing/Receiving labels and omit parties for meeting minutes. Letters display greeting → body → closing/signature; billing documents place saved totals after items and before payment notes; signatures/approvals follow body sections. Invoice/quotation `LineItemsEditor` supports description, quantity and unit price, stored as a versioned JSON string in the existing `items` value; `DocumentItems` renders rows and quantity × price amounts. Preserve legacy free text verbatim (no guessed prices); document subtotal/tax/total remain manually reviewed. Never change API payload types or rewrite existing saved values on read.

- **Documents are paper, not cards:** Anywhere a document is shown on screen (the preview `SidePanel`, the editor's live preview column and its phone preview panel, the shared document view), wrap the `TemplateDocument` in `DocumentPaper` (`components/commons/document-paper`) and put it on a grey desk (`bg-base-200` with `p-4 sm:p-6`; a desk inside the white panel may be `rounded-box`). The sheet has square corners, no border, `shadow-paper` (the `--shadow-paper` token, a contact shadow plus a soft drop, kept for paper only) and is at least one A4 page tall. Keep it narrower than any card in the same stack (the preview's info card), so it never lines up like another card. `TemplateThumbnail` draws the same paper itself (white, square, `shadow-paper`; `elevation="small"` and `tiny` for list-row thumbnails about 40–56px wide), so callers never add rounding, a border or `shadow-soft` around it. The template styles' `paper` classes carry only a style's own frame (brutalist's black rule), never rounding or a hairline border. PDF export renders the document bare, so none of this reaches a printed page.
- **Empty fields:** Placeholder text (e.g. "Client address", "Agreement reference", "Name / signature") is an editing aid only. `TemplateDocument` leaves empty fields blank by default, so saved previews, thumbnails, shared copies and PDF exports never print placeholders. Only the editor's live previews (desktop column and the mobile preview `SidePanel` in `DocumentsView`) pass `showPlaceholders`. Which fields count as not filled in comes from `getEmptyDocumentFields` (`src/lib/documents/empty-fields.ts`); `title`, party phone/email/BRN and the recipient signature are optional and never flagged.
- **Saving with empty fields:** The first Save/Create/Duplicate click with empty required fields does not save. It turns on the yellow highlight (`highlightedFields` → `<mark class="template-document-missing">`, `bg-golden-harvest/70`, see `missing-field-class-name.ts`), shows a `warning` toast (the cue mobile users see, since the preview is hidden there), and opens a `ConfirmDialog` "Some fields are empty" listing the field labels, with "Fix document" (closes it, keeps the highlights) and "Save anyway" (saves; empty fields stay blank). Highlights are recomputed from the live draft, so a field loses its highlight as soon as it is filled, and they reset whenever the editor opens or closes. The CV layout (`CvDocument`) is not covered yet.

Breaks never cut through `header`, `dl > div` (party/meta blocks), `tr`, `li` or `[data-pdf-keep]` elements; `[data-pdf-keep]` elements sharing a value form one block (totals use `data-pdf-keep="totals"`, so subtotal/tax/total always move to the next page together). `h3` headings stay with roughly two lines of what follows. Inside long free text, breaks fall on a blank pixel row between lines. Mark any new block that must not split with `data-pdf-keep`, and keep section headings as `h3`.
  - **html-to-image capture pitfalls:** Break positions are measured on the live DOM, so the capture must lay out identically. html-to-image copies each element's computed `height` inline, and fetches every `<img>` (a failed fetch rejects the whole export, so use inline SVGs such as `DokimentsMark` in printable markup, never `<img>`); likewise do not use `<caption>` (or anything else that sits outside a table's computed height) inside tables in printable documents; it stretches every row in the capture and pushes page breaks into the wrong place. Use an `h3` above the table with `aria-label` on the table instead (as `DocumentItems` does). When changing printable markup, generate a multi-page PDF (e.g. an invoice with 9–30 line items) and check that rows, totals and the footer break cleanly.

## 6b. SEO

- **One origin:** every absolute URL (metadata, sitemap, robots, JSON-LD) comes from `siteUrl` in `src/lib/seo/site.ts` (`NEXT_PUBLIC_SITE_URL`, fallback `https://dokiments.com`). Never hard-code a domain elsewhere.
- **No inherited canonicals:** the root layout sets defaults only (search-focused `defaultTitle`/`defaultDescription`, keywords, robots, icons) and must never set `alternates.canonical` or `openGraph.url` — every child page would inherit them and claim to be the home page. Next.js merges metadata shallowly, so public pages export `pageMetadata({ title, description, path })`, which sets their own canonical, Open Graph and Twitter objects. Titles go through the `%s | Dokiments` template — never write "| Dokiments" into a page title.
- **Private routes:** signed-in and utility pages (dashboard, my-*, marketplace, subscription, settings, forgot-password, offline) export `privatePageMetadata(title)` (`noindex, nofollow`). Client-component pages get it from a sibling `layout.tsx` (see `src/app/offline/layout.tsx`). They are also disallowed in `robots.ts`; keep that list in sync with `PROTECTED_PREFIXES` in `src/proxy.ts`.
- **Sitemap:** list only public, indexable pages. Routes behind `proxy.ts` redirect crawlers to `/sign-in`, so they never belong in `sitemap.ts`.
- **Structured data:** the home page renders `homeStructuredData` (`src/lib/seo/home-structured-data.ts`: Organization with VISH studio as parent and its social `sameAs`, WebSite, SoftwareApplication with a free `Offer`); `Faq` renders the FAQPage schema from `faq-items.ts`, so FAQ copy changes update it automatically. Always serialise JSON-LD with `toJsonLd` (escapes `<`, per the Next.js JSON-LD guide).
- **Copy:** lead public titles and descriptions with what people search for — invoice, quotation/quote, contract, receipt templates for small businesses and freelancers — plus the differentiators (client prefill, PDF export, free to start). Keep exactly one `h1` per page (the hero's typed headline on the home page).

## 8. Verification Checklist

Before declaring a task complete, verify stability with:

1. `npm run lint` — Zero syntax or formatting style errors.
2. `npx tsc --noEmit` — Compiles cleanly without TypeScript type mismatches. To reproduce CI, type-check a temp copy without `.next` (see `.github/copilot-instructions.md`, "CI gotchas"); never move or copy `.next` inside the repo.
3. `npx vitest run --project storybook <pattern>` for the stories you touched (stories are the component tests), and `npx vitest run --project node <path>` if you changed helpers under `src/lib/`.
4. Check the change in the running app (`dev` in `.claude/launch.json`) or Storybook (`storybook`) at mobile (390px) and desktop widths.
   **Always end a UI task by showing the user a screenshot** of the changed UI (cropped or zoomed to the change, with desktop and mobile if the layout differs) as the last thing in the reply, so they can see the result without opening the app. If no screenshot was possible, say why.
5. If printable document markup or the PDF generator changed, export a multi-page PDF and inspect every page (breaks, totals, footer alignment, page numbers).

Specialist subagents in `.claude/agents/` (`ui-designer`, `qa-tester`, `performance-optimizer`, `api-security-reviewer`) apply these rules; keep them in sync when this skill changes.
