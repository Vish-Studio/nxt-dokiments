# Dokiments UI

As an elite Fullstack Engineer and Award-Winning UI/UX Designer specialized in high-conversion marketing sites and ultra-clean dashboard apps:

## 1. Code Architecture & Component Hygiene

- **Strict Anti-Bloat Rule:** NEVER write multiple sub-components within the same file. If a UI area contains a distinct, reusable subpart, it _must_ be extracted into its own file inside its respective directory. Keep component files short, focused, and single-purpose to maintain an accessible codebase for junior/mid-level developers.
- **Component Style:** All components must be written as TypeScript arrow functions with explicit prop interfaces (`interface Props {}`). They should also include their component name as their first classname (e.g., `<div className="template-card">` for `TemplateCard`).
- **Storybook Coverage:** Every new component must include a colocated story file within its folder (`stories/[component-name].stories.tsx`).
- **Storybook Sidebar Titles:** Every story meta must set an explicit `title` grouped by component bucket only (`Commons/Button`, `Dashboard/Sidebar`, `Website/Hero`). Do not allow Storybook to infer paths that expose `stories` as a sidebar nesting level.
- **State Management:** Shared global UI state belongs in `src/stores/ui-store.ts`. Use it sparingly (e.g., sidebar state, theme tracking); prefer props or local React state for localized hierarchies.

## 2. Strict Directory Structure

All UI components must reside exactly within one of these four subdirectories under `src/components/`:

- `src/components/commons/` — Globally reusable foundational atomic elements (buttons, inputs, dropdowns, modals, loaders) that extend DaisyUI with a flat design language.
- `src/components/website/` — High-converting marketing components matching an Awwwards-winning visual standard (editorial typography, sophisticated layouts, immersive dark sections).
- `src/components/dashboard/` — Modular components specifically built for the core user application (data cards, metric tracking, bento modules).
- `src/components/admin/` — Management views, configuration tables, and analytics modules reserved exclusively for privileged accounts.

## 3. Visual & Aesthetic Guidelines (Awwwards x Bento Style)

- **Aesthetic Direction:** Merge a premium, minimalist dark-mode canvas with "flat design" principles. Avoid heavy gradients, soft outer blurs, or realistic skeuomorphism. Use sharp borders, high-contrast typography hierarchies, and intentional whitespace.
- **Bento Grid Dashboard:** Construct dashboard layouts using structured CSS Grid tracks (`grid-cols-1 md:grid-cols-3 lg:grid-cols-4 gap-4`). Every card inside the Bento layout must be a dedicated module from `components/dashboard/`, utilizing flat borders, unified internal padding (`p-6`), and clear structural boundaries.
- **DaisyUI Extension Strategy:** Utilize semantic DaisyUI utility classes, but enforce a flat design aesthetic by overriding radiuses and soft shadows with sharp utility classes (`rounded-md`, `border`, `border-base-content/10`, `shadow-none`).
- **Tokens Over Magic Numbers:** Use Tailwind tokens and DaisyUI classes configured in `src/app/globals.css`. Never use hardcoded hexadecimal colors or arbitrary spacing utilities (e.g., use `p-6` or `gap-4` instead of `p-[23px]`).
- **Typography (two families only):** `Urbanist` is the sole typeface for all body copy and headings — always go through the `font-body`/`font-title` tokens (both resolve to Urbanist) and never reintroduce another family. `Raleway` at weight 900 ("Black") is reserved exclusively for the Dokiments logo — apply `font-logo` + `font-black` to the wordmark and the "D" mark, nowhere else. Fonts are loaded via `next/font/google` in `src/app/layout.tsx` (`--font-urbanist`, `--font-raleway`).
- **Control Hierarchy:** Keep buttons, inputs, and tabs visually distinct. Primary buttons are solid black (`btn-primary`, white text — never golden); `secondary` is a soft grey fill; `outline` is bordered; `ghost` is text-only. All text CTAs across the website and dashboard use the compact rectangular `rounded-field` radius, matching the subscription plan actions; do not use `rounded-box` or `rounded-full` for CTA buttons. Icon-only controls retain their intentional circle/square shapes. Inputs/selects use a slight grey fill (`bg-base-200`) with a calm focus treatment (`focus:border-nox-noir focus:ring-2 focus:ring-nox-noir/15`), never heavy double outlines. Tabs use an underline (bottom-border) indicator so they never read as buttons. Do not use the retired deep-purple utility class; the product palette should rely on `bg-nox-noir`, `bg-golden-harvest`, and the pastel page colors.
- **Dropdowns:** Use the shared `Dropdown` component from `components/commons/dropdown` for every application selection menu. Its exported `dropdownControlClassName` is the canonical sort/filter treatment: a `rounded-field`, `border-steel-mist` control on `bg-base-200`, with compact typography and a calm expanded state. Compose responsive width or size adjustments onto that class instead of creating native `<select>` controls or bespoke menu treatments. Dropdown option lists use the same bordered base surface, grouped labels, and checked selected state.
- **Website Hero Discipline:** Marketing hero sections must be high-conversion and edited, built from the dashboard's own visual parts so the site and app feel like one product. Keep one clear promise and two CTAs maximum, and keep all hero content inside the main white hero container (`grid lg:grid-cols-[0.88fr_1.12fr]`, both columns inset `p-3 lg:p-4`).
  - **Left column (`HeroIntro`, client component):** a `rounded-box` intro card that mirrors the dashboard welcome card and walks through the app's process in three plain steps (`hero-intro-steps.ts`). Each step owns a tone, a headline (`lead` + white-highlighted `highlight`) and a description: 01 **Pick a template** (`bg-golden-harvest` — the brand golden, matching the dashboard welcome card — keeps "Business documents without the **blank page.**" as the server-rendered default `h1`), 02 **Add your client** (`bg-play-blue`, My Clients; "Your client's details, **filled in for you.**"), 03 **Send the PDF** (`bg-play-purple`, My Documents; "A polished PDF, **ready to send.**"). The active step sets the card background (`transition-colors duration-500`) and swaps the copy (re-keyed with `feature-tab-details-enter`); the copy block has `lg:min-h-60` so the CTAs never jump between steps. Card order: the white/65 uppercase `Sparkle` pill ("Document workspace"), the step headline (`text-4xl sm:text-5xl`, highlight is a `bg-white` `whitespace-nowrap` mark) and description, `HeroActions` (black primary; Sign In gets a white fill via `secondaryClassName`), then the three `HeroFeatureTile` step buttons in an `ol` (`grid sm:grid-cols-3`), then `HeroCredit`. Tiles are slim rectangles (`rounded-field`, `p-2`, three across in `grid grid-cols-3 gap-2`): a `size-8` icon tile in the step's tone, then a one-word `label` ("Template", "Client", "Send PDF") over the progress track with the step number at its end, the two lines together spanning the icon's height. The full step `title` is the button's `aria-label`. The active tile is solid white and its track fills; inactive tiles are `bg-white/45` with an empty track. Below `sm` tiles show only the icon on the tinted tile background — the label and number are hidden and the track stays mounted but `invisible`, so its animation (and autoplay) keeps running; never `display: none` the track or autoplay stops. **Reveal animation (pure CSS, slow and eased):** every step's headline renders through `HeroTypedHeadline` — each character is its own `.hero-type-char` span faded in over 0.4s on a 0.055s stagger, the white highlight mark fades in as typing reaches it, and a `.hero-type-caret` blinks three times (0.9s) after the last character, then disappears. The `h1` keeps the full text in the server HTML and gets its accessible name from `aria-label` (character spans are `aria-hidden`). Blocks fade up with `.hero-reveal` (1.1s, `--reveal-delay`). All hero easing is the symmetric `cubic-bezier(0.45, 0, 0.55, 1)` ease-in-out — never snappy ease-out curves here. On first load (typing starts at 0.4s) the order is: pill, headline, paragraph (+0.2s after typing), stepper (+0.7s), credit (+1.1s), CTAs (+1.5s); the whole reveal settles around 5.5s. On every step change the copy block is re-keyed, so the new headline types in the same way (from 0.25s) and its paragraph fades up after it; the stepper, credit and CTAs stay put, and the card background eases to the new tone over `duration-1000 ease-in-out`. Delays are computed in `HeroIntro` from each headline's length. All reveal/typing animation is disabled under `prefers-reduced-motion` (the caret is `display: none`). Autoplay follows the shared pattern: the active tile's `.hero-step-progress` bar (9s in `globals.css`, long enough for a step to type in and still be read) advances to the next step on `animationend`. The very first run is held back 6s after page load, until the load reveal has settled (`.hero-step-progress-delayed`, `animation-fill-mode: both` so the bar stays empty while waiting); any advance or click ends the delay. Clicking a tile selects it and restarts the timer; no hover pause; disabled under `prefers-reduced-motion`. `HeroCredit` closes the card: "© year Dokiments · A digital product of vish.studio", `text-xs` muted, linking to vish.studio in a new tab (no Vish Studio icon — the SVG is white-filled and vanishes on light surfaces). The whole column must fit `lg:h-[calc(100vh-8rem)]` at 1280×800.
  - **Right column (`HeroProductMockup`):** product photography only — `hero-laptop-rock.webp` (`object-cover`, `object-[40%_50%]`) under a light `bg-nox-noir/15` overlay, with the `hero-mobile-cutout.webp` iPhone floating bottom-right (`website-float-delayed`) to show mobile support. No labels, chips or cards on the photo.
  - When changing the hero, screenshot it at 1440×900, 1280×800 and 390px wide and check nothing is clipped.

## 4. App Shell & Layout Rules

- **Shell Division:** Main app shell pieces live under `src/components/dashboard/` and are broken down into: `app-shell`, `sidebar`, `topbar`, and `content-container`. Do not prefix these component names with `dashboard`.
- **Topbar Control:** The topbar sits on the dark app background above the white main content panel and aligns with the sidebar logo row. It shows _only_ the page title and right-side action items. Personalized copy like `Hello, Anthony!` belongs inside the main canvas panel, never the topbar.
- **User Navigation:** The topbar user menu lives in `user-dropdown`; never render the raw user email inside the topbar trigger.
- **Sidebar UX:** When the desktop sidebar is collapsed, clicking the logo expands it. Do not show a duplicate hamburger or toggle icon in the collapsed view. Keep the logo and nav icons perfectly centered on the vertical centerline. Sidebar bottom controls must separate into `theme-toggle` placed directly above `settings-nav-item`.
- **Onboarding tour:** New accounts land with `?welcome=1`, added by `SignUpForm` to both its email redirect and its "Sign up with Google" `next` path (the auth routes and Firebase helpers stay untouched). `OnboardingLauncher`, mounted once in `AppShell`, opens `OnboardingDialog` from that flag and strips it from the URL; open state lives in `ui-store` so the sidebar's "Getting started" row (`SidebarOnboarding`, directly above "Send feedback") reopens the same tour. Steps live in `onboarding-steps.ts`: Welcome ("Hi {first name}!" greeting; its golden image container shows the laptop-on-rock `home-mockup.svg` sitting on the container's bottom edge), then the template system in order — Marketplace → My Templates → My Documents — then My Clients and Plans, each on its area's page tone. Copy is short and plain and names real buttons and pages; each point is a bold label over one lighter sentence, under a large title and a darker lead line. The dialog mirrors the sign-in page: inset by `p-3`, a rounded tone container on the left whose visuals crossfade like `AuthShowcaseSlide` (`hero`, `framed` and `wide` layouts), with the copy, progress and actions on the right. On desktop a small black wordmark sits centred at the top of the image container on every step, outside the crossfading visuals so it never fades. It is full screen below `md`, with a top row holding the wordmark (left) and the close button (right) above the image container, and a centred card from `md` up.
- **Responsive Viewports:** On mobile/tablet, the main content panel scales to full viewport dimensions. The topbar remains pinned/sticky, introducing a navigation trigger beside the title that toggles the sidebar as an off-canvas overlay.

## 4b. Auth Pages

- **Shared shell:** Sign in, sign up, and forgot password all render through `AuthLayout` (`src/components/commons/auth-layout/`). It is a full-viewport white split screen with no website `Header`/`Footer`: the left half (desktop `lg+` only) holds the `AuthShowcase` inside `p-3`, sticky at `h-dvh`; the right half centres a `max-w-md` column with the black "D" mark (`/images/svg/icon-black.svg`, linking home), a centred `font-title` heading, a short description, the form, an optional centred text footer, and `HeroLegal` pinned to the bottom. Auth pages set `viewport.themeColor` to `#ffffff`.
- **Forms stay separate:** Redesigns of the shell must not touch `SignInForm` / `SignUpForm` / `ForgotPasswordForm` internals. Page-level copy (title, description, footer links) lives in the page file.
- **AuthShowcase:** A five-step product tour (Marketplace → Templates → Documents → Workspace → Plans) defined in `auth-showcase-slides.ts`. Each slide is a flat, gradient-free field in its product area's page-banner tone (teal, pink, purple, golden, blue) with the matching illustration framed as a `rounded-box` card and noir editorial copy at the bottom. Slides crossfade; they are all mounted so images are ready before they appear.
- **Stepper timing:** The bottom stepper is an accessible `tablist` (arrow keys move between steps). The active step's progress bar is the autoplay timer: its `auth-showcase-progress` CSS animation in `globals.css` runs 5s and its `animationend` advances the slide, so change the duration there, not in JS. Autoplay pauses on hover/focus and is disabled under `prefers-reduced-motion` (the active bar shows full).
- **Mobile:** The showcase is hidden below `lg`; the form column is the whole page. In its place, the intro (logo, heading, description) becomes a golden `bg-golden-harvest` `rounded-box` panel inset by the same `p-3` gutter as the desktop showcase, with the form below it; from `lg` up the intro is a plain centred header.
- **Sign-in form order:** `GoogleSignInButton` leads (full width, outlined, `rounded-field`), then an "or continue with email" divider, email, password with a right-aligned "Forgot password?" link beneath it, and the black `primary` "Sign in" button directly after the credentials.
- **Promo code:** Optional fields never sit between credentials and their submit button. The promo field lives inside `PromoCodeDisclosure` (a native `<details>` toggle reading "Have a promo code?") below the submit button. When open it shows the golden callout box (`rounded-box border-golden-harvest/40 bg-golden-harvest/10 p-4`, gift icon, campaign label and code from `activePromoCode`) with the input inside it. It stays mounted while collapsed so the form keeps owning its state and the code still reaches both the submit body and the Google link; when collapsed with a value, the toggle shows the entered code.

## 5. Integrations & Guards

- **Icons:** Use Phosphor Icons (`@phosphor-icons/react`) exclusively for all dashboard controls, navigation, and state indicators.
- **Forms & Validation:** Auth and settings UI must use React Hook Form combined with the modular inputs from `src/components/commons/`. Keep form containers isolated in their own folder tracks.
- **Firebase Infrastructure:** Client integrations live in `src/lib/firebase`, consuming REST APIs wired through `NEXT_PUBLIC_FIREBASE_API_KEY`, `NEXT_PUBLIC_FIREBASE_AUTH_DOMAIN`, and `NEXT_PUBLIC_FIREBASE_PROJECT_ID`.
- **Dev Auth Bypass:** Local development may bypass Firebase auth with `NEXT_PUBLIC_DEV_AUTH_BYPASS="true"`. The bypass must remain gated by `process.env.NODE_ENV === "development"` and should use `src/lib/dev-auth.ts` rather than scattering mock-user logic across components.
- **RBAC:** Application roles map to `superadmin`, `free`, `silver`, `gold`, and `special`. Defaults to `free`. Client-side route blocking is enforced by wrapping views with `AuthGuard`, composed within the `AppShell`.

## 6. Marketplace, Templates & Documents

- **Form section icons:** Pair each `TemplateForm` legend with a neutral Phosphor icon: file for document details, user for sender, identification card for recipient, list for content/items, currency for amounts, and signature for closing. Use `size-5`, `shrink-0`, `gap-2`, and `aria-hidden`; retain visible titles without adding explanatory text or decorative icon backgrounds.

- **Document editor forms:** `TemplateForm` uses title-only sections with no explanatory paragraphs: Document details, Your details, Client details (invoice/quotation/receipt; otherwise Recipient details), Items or Content, Amounts, and Signatures & closing. Preserve NDA party labels and hide empty groups. Sections are an accordion of `FormAccordionSection`s (semantic fieldsets whose legend is the toggle button): only one is open at a time, starting with Document details; each ends with a black `primary` "Next" button ("Save" on the last) that marks it complete, closes it and opens the next. Values still flow to the draft on every change, so the button never calls the API. Only Document details starts open, so stories/tests that touch other sections (e.g. the sender block or `ClientPicker` in Client details) must first click that section's header button (accessible name starts with the section title). Use subtle top dividers and `gap-4` between fields. Keep document name in Document details and `ClientPicker` inside Recipient. `ClientPicker` owns the whole Client/Recipient section: `TemplateForm` passes the section's rendered recipient inputs through `renderRecipientFields`, and the picker decides whether to show them. Two `ClientSourceOption` radio cards in a `radiogroup` (`grid sm:grid-cols-2`, styled like the dashboard snapshot rows: `size-9` pastel icon tile, title + one-line detail; selected = `bg-base-100` with `border-nox-noir`, unselected = `bg-base-200`) choose the side. **Saved client** (blue `AddressBook`) hides the inputs entirely: the `Dropdown` of saved clients, then a read-only `ClientSummaryCard` of the chosen client (avatar in its stable `getClientAccentClass` tone, company + contact name, then only the email/phone/address/BRN it has); picking one clears the recipient keys and merges `clientPrefillValues`. **New client** (golden `UserPlus`) shows the inputs; once a recipient name is typed, `SaveClientPrompt` appears under them — a blue "Save {name} for next time?" box with a black `Save client` button — or, if the details already match a saved client (`findMatchingClient`: same email, or same company/contact name, in `src/lib/clients/clients.ts`), a small green "already in My Clients" line instead. The cards only show when the user has saved clients; with none, the section is the inputs plus the prompt. The starting side follows the document: a recipient matching a saved client opens on Saved client with it shown; hand-typed details open on New client so they are never hidden. Switching sides clears the recipient keys (`clientFieldKeys`). "Save client" opens a `ConfirmDialog` ("Save {name} to My Clients?", listing the email and phone) and, on confirm, saves directly through `useCreateClientMutation` — no form. The document has one recipient name, so it fills both `companyName` and the contact `name` (renamable later in My Clients); email/phone/address/BRN come from the recipient fields via `clientInputFromValues`. Because `ClientSchema` requires an email and phone, the prompt's button stays disabled with "Add their email and phone above…" until both are filled (email must look valid), and templates without `toEmail`/`toPhone` fields show no save prompt at all. On success it toasts, closes the dialog and switches to Saved client with the new client's card; on error it closes and shows an error toast. Party inputs follow name → phone → email → address → BRN. Grouping is presentation-only and must preserve all field keys, values and change callbacks, including unknown saved-template fields in Content.

- **Document layout:** `TemplateDocument` reuses the borderless two-column `TemplateParties`: name → phone number → email → multiline address; BRN follows when present. Optional blank contacts are omitted. Use `mb-8` before metadata/body. `withPartyContacts` adds optional sender/recipient contact inputs for existing templates without rewriting snapshots; prefill uses the same fields. Preserve NDA Disclosing/Receiving labels and omit parties for meeting minutes. Letters display greeting → body → closing/signature; billing documents place saved totals after items and before payment notes; signatures/approvals follow body sections. Invoice/quotation `LineItemsEditor` supports description, quantity and unit price, stored as a versioned JSON string in the existing `items` value; `DocumentItems` renders rows and quantity × price amounts. Preserve legacy free text verbatim (no guessed prices); document subtotal/tax/total remain manually reviewed. Never change API payload types or rewrite existing saved values on read.

- **Document names in the UI:** Show plain-language names that individuals and businesses both understand (Contract, Invoice, Quotation, Receipt, NDA, Scope of Work, Change Request, Contract Update, Meeting Notes, Status Report, Business Letter, …). They live in `documentTypeLabels` (`src/lib/market-place/document-labels.ts`) and are display only. Never rename `documentBlueprints[type].name`: it is the canonical name seeded into Firestore by `scripts/seed-templates.ts` and frozen into saved document snapshots. Render category labels with `getDocumentTypeLabel(type)` and template/snapshot names with `getTemplateDisplayName(template)`, which swaps a canonical name for the plain label and keeps custom names unchanged; never render `template.name`, `templateSnapshot.name` or `documentBlueprints[type].name` directly. Keep labels short and plain; the marketplace category chips show them in full on one line.

- **PDF export:** PDFs are generated only in `DocumentExportDialog`, which renders the print `TemplateDocument` and the `PdfWatermark` footer off-screen at 794px and passes both to `generateDocumentPdf(element, { footer })` (`src/lib/pdf/generate-document-pdf.ts`). The on-screen document, previews and thumbnails never show the watermark.
  - **Watermark footer:** `PdfWatermark` (`components/dashboard/pdf-watermark`) is a `border-t-2 border-nox-noir` rule matching the classic header, then a three-column grid: the inline `DokimentsMark` "D" icon (`h-5 w-4.5`; `components/commons/dokiments-mark`, viewBox cropped flush to the glyph) + "Made with **Dokiments**" (wordmark in `font-logo font-black`) on the left, "Page x of y" centred (only when there are 2+ pages), `www.dokiments.com` on the right, all `text-xs` muted noir. Its horizontal inset must come from `templateInsetClassName[template.style.id]` (exported by `template-document.tsx`) so it lines up with each style's body padding; update that map whenever a style's body padding changes. The generator fills the page label on a detached clone of the footer (`data-pdf-page-label`), never on React-managed DOM, and stamps it on every page.
  - **Page layout:** A4, 6mm page margin, 6mm minimum gap between content and the footer rule (content that would come closer moves to the next page), and continuation pages start 4mm lower than page 1. Change these via the constants at the top of the generator.
  - **Page breaks:** The document is captured once with html-to-image and sliced per page. Breaks never cut through `header`, `dl > div` (party/meta blocks), `tr`, `li` or `[data-pdf-keep]` elements; `[data-pdf-keep]` elements sharing a value form one block (totals use `data-pdf-keep="totals"`, so subtotal/tax/total always move to the next page together). `h3` headings stay with roughly two lines of what follows. Inside long free text, breaks fall on a blank pixel row between lines. Mark any new block that must not split with `data-pdf-keep`, and keep section headings as `h3`.
  - **html-to-image capture pitfalls:** Break positions are measured on the live DOM, so the capture must lay out identically. html-to-image copies each element's computed `height` inline, and fetches every `<img>` (a failed fetch rejects the whole export, so use inline SVGs such as `DokimentsMark` in printable markup, never `<img>`); likewise do not use `<caption>` (or anything else that sits outside a table's computed height) inside tables in printable documents; it stretches every row in the capture and pushes page breaks into the wrong place. Use an `h3` above the table with `aria-label` on the table instead (as `DocumentItems` does). When changing printable markup, generate a multi-page PDF (e.g. an invoice with 9–30 line items) and check that rows, totals and the footer break cleanly.

- **Template catalog:** Templates live in `src/lib/market-place/` as `<style>/<document>.ts` leaf files (e.g. `classic/contract.ts`), each composing a `style` (`styles.ts`) with a document `blueprint` (`documents.ts`, the shared field definitions). The barrel `index.ts` exposes helpers: `marketplaceTemplates`, `getTemplateById`, `listTemplatesByStyle`, `canUseTier`, `tierLabels`, `getSampleValues`. Add new documents by extending `documents.ts` + a leaf per style; add new styles by extending `styles.ts` + leaves.
- **Sample content:** `sample-data.ts` holds realistic dummy values per document type. `TemplateThumbnail` and the preview default to these so users see a filled document, not empty placeholders.
- **Styles & tiers:** Styles map to subscription tiers (Classic = free, Modern = silver, Minimal = gold). Tier and status labels use the shared `Badge` component from `src/components/commons/badge/badge.tsx`: Free = green (`bg-success`), Silver = golden, Gold = black/noir (mirrors the plan-card backgrounds). Gating is via `canUseTier(role, tier)` — any tier can be previewed, but saving/using a locked tier requires upgrading (`/subscription`).
- **Marketplace layout:** Categorized by style; each style's cards render in a horizontal `Carousel`. The page opens with the full-width `MarketplacePromoBanner` before category navigation. It is a four-slide news carousel: documents/overview → Clients workspace → promo offer → growing template library. Preserve its supplied left-copy/right-visual composition, with one contextual existing `LinkButton` per slide. Keep the copy compact and dashboard-consistent: a `text-3xl`/`sm:text-4xl` heading, `text-base`/`sm:text-lg` detail, and medium CTA. Vertically center the complete left content group, with the CTA directly beneath the text rather than distributed to the banner edge. Use the supplied `public/images/svg/icon-vish-studio.svg` as an oversized, dark, low-opacity watermark behind the left copy, offset so only its right half emerges from the banner's left edge. Clients use the palette blue consistently: `My Clients` has the `blue` page-header tone, and the related marketplace slide uses `bg-play-blue`. Documents/overview uses `bg-golden-harvest`, promo uses `bg-play-purple`, and templates uses `bg-play-pink`. The banner has no border and no visible carousel navigation controls; it advances automatically. Use dark editorial copy and a black shared rectangular CTA; do not add overlays or gradients. Each slide's `imageSrc` is independently configurable, so temporary placeholder visuals can be replaced with final product imagery without changing the banner layout. The yellow overview slide uses `public/images/mockups/marketplace/home-mockup.svg`; clip the embedded screen rectangle's top edge in that SVG to suppress source-edge artifacts. On every slide change, use smooth, hardware-friendly easing: animate background color first, copy second, then the right visual; use opacity and transform only, provide enough stagger for each layer to settle, and disable all three for reduced-motion preferences. `MarketplacePromoCarousel` owns one taller fixed `h-96` frame at every breakpoint; each `MarketplacePromoSlide` must use `h-full`, never its own height token, so all content variants occupy the same unclipped banner height. Use the dedicated `MarketplacePromoCarousel` here—not the shared sliding `Carousel`—so a fixed promo container swaps slides with a short fade, avoiding adjacent slide edges during transitions. Marketplace categories use the shared `Carousel` at every breakpoint with `navigationPlacement="header"`, placing visible previous/next controls beside “Browse by category” to signal the horizontally scrollable rail. Each `MarketplaceCategoryTile` is a content-width chip (`w-auto whitespace-nowrap`, `h-10` compact / `h-12` from `lg`): Phosphor icon on the left and the full label on the right, never truncated or line-clamped. Active chips are solid noir with a filled icon. `MarketplaceCategoryNavSkeleton` mirrors the same chip shape with varied label widths.
- **Preview:** Opens in the reusable right-hand `SidePanel` drawer (flat, slides in via `.side-panel-enter`), rendering the `TemplateDocument` with sample content.
- **Persistence & flow:** Owned templates live in `templates-store` (ownership only — no values), created documents in `documents-store`; both are per-`uid` and persisted with zustand `persist`. Flow: Marketplace saves a template → **My Templates** is a read-only gallery of owned templates (thumbnails, no editing) → **Documents** creates/edits a concrete document from an owned template (name + `TemplateForm` on the left, live `TemplateDocument` render on the right).
- **Reusable building blocks:** Prefer `PlanCard` (used by subscription + website pricing), `TemplateDocument` (style-aware renderer), `TemplateThumbnail`, `Carousel`, and `SidePanel` over re-implementing these patterns.

## 6b. SEO

- **One origin:** every absolute URL (metadata, sitemap, robots, JSON-LD) comes from `siteUrl` in `src/lib/seo/site.ts` (`NEXT_PUBLIC_SITE_URL`, fallback `https://dokiments.com`). Never hard-code a domain elsewhere.
- **No inherited canonicals:** the root layout sets defaults only (search-focused `defaultTitle`/`defaultDescription`, keywords, robots, icons) and must never set `alternates.canonical` or `openGraph.url` — every child page would inherit them and claim to be the home page. Next.js merges metadata shallowly, so public pages export `pageMetadata({ title, description, path })`, which sets their own canonical, Open Graph and Twitter objects. Titles go through the `%s | Dokiments` template — never write "| Dokiments" into a page title.
- **Private routes:** signed-in and utility pages (dashboard, my-*, marketplace, subscription, settings, forgot-password, offline) export `privatePageMetadata(title)` (`noindex, nofollow`). Client-component pages get it from a sibling `layout.tsx` (see `src/app/offline/layout.tsx`). They are also disallowed in `robots.ts`; keep that list in sync with `PROTECTED_PREFIXES` in `src/proxy.ts`.
- **Sitemap:** list only public, indexable pages. Routes behind `proxy.ts` redirect crawlers to `/sign-in`, so they never belong in `sitemap.ts`.
- **Structured data:** the home page renders `homeStructuredData` (`src/lib/seo/home-structured-data.ts`: Organization with VISH studio as parent and its social `sameAs`, WebSite, SoftwareApplication with a free `Offer`); `Faq` renders the FAQPage schema from `faq-items.ts`, so FAQ copy changes update it automatically. Always serialise JSON-LD with `toJsonLd` (escapes `<`, per the Next.js JSON-LD guide).
- **Copy:** lead public titles and descriptions with what people search for — invoice, quotation/quote, contract, receipt templates for small businesses and freelancers — plus the differentiators (client prefill, PDF export, free to start). Keep exactly one `h1` per page (the hero's typed headline on the home page).

## 7. Shared Dashboard Patterns

- **Dashboard lists:** Use `DashboardList` for the responsive 12-column header, surface, and borders. Keep entity-specific row data and actions in components such as `DocumentListItem` and `ClientList`.
- **Clients collection:** `ClientList` uses a content-height responsive card grid with no outer collection surface: one column on mobile, two at `sm`, and three at `xl`. Each `ClientListItem` uses compact, fixed `h-44` cards with `p-4`, a `size-10` avatar, small name/company and contact type, and an `h-8` secondary “View client” action. Derive each avatar's stable accent from its client ID and rotate across `play-blue`, `play-teal`, `play-purple`, `play-pink`, `play-amber`, and `golden-harvest`, rather than changing color at every render. Keep Edit and Delete together in the compact three-dot overflow menu at the card's top-right; never show a red delete button in the card body. Use `border-play-blue` only as the card hover accent.
- **Continue work:** The dashboard's Continue Work card selects the latest created `UserDocument` by `createdAt` (not its most recently updated document). Render its own frozen `templateSnapshot` through `snapshotToMarketplaceTemplate` and `TemplateThumbnail`, passing its saved values, so the right-side mockup always shows the chosen template and the user's real document data. Fall back to `getTemplateById` only for legacy records lacking a snapshot. Make the outer panel a vertical flex surface and its blue latest-document card `flex-1`, so it fills every remaining pixel inside the parent `p-5/sm:p-6` inset.
- **Marketplace copy transition:** Keep the promo copy's layout stationary. Fade the title group in first, then fade the detail paragraph after a short delay; neither may use a transform. Fade the CTA after the paragraph.
- **Website FAQ:** `Faq` is a two-column grid on `lg` (`0.72fr_1.28fr`): the `SectionHeading` on the left is `lg:sticky lg:top-28 lg:self-start` so it stays pinned below the fixed `h-20` website header while the `FaqItem` list on the right scrolls. Keep `self-start` (a stretched grid item cannot stick) and keep any ancestor free of `overflow-hidden`, which also breaks sticky. Below `lg` the heading simply stacks above the list.
- **Website footer:** Use a solid `bg-nox-noir` surface with the masked Dokiments wordmark in white. Include the essential product, account, legal/cookie, newsletter, social, and install-app paths; avoid photo backdrops and decorative gradients that weaken the navigation hierarchy. On desktop, mirror the top brand/newsletter split in the lower navigation: Product/Account belong under the brand column, while Legal/Follow belong under the newsletter column. Align both its content and legal rows to the marketing site's shared centered `max-w-7xl` grid, wrapped in the standard responsive side padding; do not use a unique footer width.
- **Collection surfaces:** My Documents and My Templates use full-width, full-available-height rounded collection surfaces. Tables fill the available surface width, and the template gallery lives inside the same type of surface rather than floating on the canvas. The clients card grid is deliberately content-height. Group the collection toolbar with its surface: use `pt-6` from the page banner and `gap-2` before the collection surface.
- **Position indicators:** Every carousel and stepped flow shows its position with the shared `StepIndicator` (`src/components/commons/step-indicator/`): pill dots (the active one stretched) and a `2/6` counter, read to screen readers as "{label} 2 of 6" (`label` is `Slide` for carousels, `Step` by default). Place it to the left of the previous/next controls. Do not build bespoke progress bars or counters.
- **Save confirmations:** Confirm a successful save with a bottom toast: call `useToastStore().showToast({ message, tone })` (`src/stores/toast-store.ts`). The shared `Toaster` (`components/commons/toaster`) is mounted once in `AppShell` and in Storybook's preview, so never mount another in a page. Validation and server errors stay inline next to the form.
- **Right-side panels:** Use `SidePanel`, matching its `tone` to the active `PageBanner`: Documents `purple`, My Templates `pink`, Marketplace `teal`, and My Clients/Dashboard `golden`. Place panel actions in its `footer`.

- **Settings page:** `SettingsTabs` lays Settings out like an account-settings screen: one bordered surface with `SettingsNav` down the left (`lg+`: a sticky vertical tab list that stays put while the section scrolls — so the surface must never get `overflow-hidden` — with the active item `bg-nox-noir text-white` and a red "Log out" set apart at the bottom; below `lg`: the shared `TabMenu`, kept inside a `grid-cols-1`/`min-w-0` column so it scrolls sideways rather than widening the page) and the active section on a `bg-base-200` column on the right — an `h2` title and one-line description, then stacked white `SettingsCard`s with pastel icon tiles. Sections: My profile (`ProfileOverviewCard` — identity, plan, sign-in method and "N of 6 document details added"; then `ProfileDetailsCard`s for Personal information and Business details), Plan (`PlanAccessCard`), Security (`PasswordSettings`) and Promotions (`PromoCodeCard`). Business details mirror a client record: company name, BRN, business email, website, address. Profile cards are read-only `SettingsDetailList` grids with a grey `secondary` "Edit" button that swaps the card into a form for just its fields; a save still sends every profile field, because `update-profile` replaces the whole profile. `PlanAccessCard` lists features from `getPlanFeatures` (`src/lib/subscription/plan-access.ts`), which is built on the enforced rules (`canUseTier`, `getSavedTemplateLimit`), never on marketing copy; roles above Gold see everything unlocked and no upgrade prompt. There is no delete-account flow; do not add one without a backend route.
